# mboard v1 spec

mboard is a personal Kanban desktop app for macOS: an Electron menu-bar app with a React + TypeScript UI. Its only data store is a folder of markdown task files inside an Obsidian vault.

Every decision here was settled on the wayfinder map, "Map: mboard v1, a Kanban board stored in an Obsidian folder" (GitHub issue 1). Each section links the ticket that holds its rationale. Terms follow `GLOSSARY.md`; the architectural decisions are in `docs/adr/`.

## 1. Scope

**In v1**

- First run and board folder setup.
- One board with five fixed columns.
- Tasks: create, edit, comment, move, reorder, complete, archive, restore and delete.
- History log with ledger data and revert, working-day age tiers, due dates and reminders.
- Project autocomplete, search and filters, and an archived view.
- Live pick-up of outside edits.
- Running from the menu bar, and open at login.
- Settings, and app updates from public GitHub releases ([ADR 0004](../adr/0004-in-app-updates-from-github-releases.md)).

**Out of v1:** see the map's Out of scope section. Notably: custom columns, times on due dates, editing comments in the app, project rename and merge, multiple boards, attachments, agent integration, signing for distribution, and any network access other than app updates. ADR 0004 reopened network access for app updates only.

## 2. Domain rules

### Columns and lifecycle

Sources: [Task lifecycle](https://github.com/marcusrohden/mboard/issues/5) and ADR 0006.

- **Columns:** `To do`, `In progress`, `Internal`, `With client`, `Done`, in that order. They are fixed.
  - **Internal:** the task is waiting on someone in my organisation.
  - **With client:** the task is waiting on the client.
  - A task can move between any two columns.
- **Complete:** a task is complete when it's in Done. Moving it out of Done reopens it.
- **Archive:** only from Done, one task at a time, or **Archive all** on the Done column (with a confirmation).
  - The file moves to `archive/` and gains `archived: <now>`.
- **Restore:** moves the file back to `tasks/` at the top of Done, and removes `archived`.
- **Delete:** any task, after a confirmation. The file goes to the macOS Trash. No history entry.
- **Order:**
  - Manual, stored in the `order` number property.
  - A new task, or one moved by a button, goes to the top of its column. A dropped task lands where it's dropped.
  - Sorting: `order` ascending with missing orders last, then `created` descending, then title.
  - Reordering writes only the moved file. If there's no room between neighbours (a gap under 1e-6), the column is renumbered 1..n, and those writes don't count as updates.

### Updates, history and comments

Source: [Timestamps, history log and staleness colours](https://github.com/marcusrohden/mboard/issues/6).

**An update** sets `updated` to now and appends exactly one history entry, with ledger data (see Ledger). A revert first removes the entries after its target. These are updates:

| Change | History text |
| --- | --- |
| create | `Created in To do` (the column it was created in) |
| title | `Title changed from "Old" to "New"` |
| description | `Description edited` |
| project | `Project changed from (none) to Acme website` (`(none)` for empty) |
| due date | `Due date changed from (none) to 2026-11-20` |
| move to another column | `Moved from To do to In progress` |
| comment | `Comment added` |
| archive | `Archived` |
| restore | `Restored to Done` |
| revert | `Reverted to 16 Nov 14:02 — 3 changes discarded` (see Revert) |

- **No-op edits:** saving a field with an unchanged value is not an update.
- **Not updates:** reordering within a column, renumbering, and outside edits.
- **Comments:** append-only in the app, apart from a revert removing the comments added after its target. Text is trimmed and can't be empty.

### Ledger

Source: ADR 0005.

- **Ledger data:** every update stores, with its history entry, exactly what it changed and when, to the second (`at`, `YYYY-MM-DDTHH:mm:ss`). The visible line keeps its minute. The format is in section 3.
  - **Value changes** `{ field, from, to }` for `title`, `status`, `project`, `due`, `description` (the whole text, old and new) and `archived`, in that order. `null` means empty. A change to a field mboard no longer tracks, such as `responsibility` (ADR 0006), is kept in the file but never reverted.
  - **Comment changes** `{ field: 'comments', added, removed }`, listed after the value changes.
  - **Create** records each field that starts with a value, each from `null`.
  - Archive records `archived`; restore records `archived` and, when it differs, `status`.
- **Legacy entries:** history lines without ledger data, written before the ledger or by hand. They show as usual but can't be reverted past.
- Outside edits are still never recorded (ADR 0001).

### Revert

Source: ADR 0005.

- **Revert to entry k** gives the task its state right after entry k (entries count from 0, oldest first).
  - The entries after k are walked from newest to oldest, and each change is undone: a field gets its `from` value back, a comment the change added is removed (the last one with the same time and text, skipped if it's already gone), and comments it removed come back in date order.
  - A field that no entry after k touched keeps its current value, so outside edits to it survive. An outside edit to a field that a later entry did touch is replaced by that entry's `from`.
  - Changes to fields this version doesn't track are kept in the file but not undone.
- **Allowed** only when all of these hold:
  - the task isn't archived (restore it first)
  - k isn't the last entry
  - entry k has a date
  - every entry after k has ledger data
  - the state after k isn't archived
- **What it writes**, in one read-modify-write:
  - The history keeps entries 0..k, then gets one new entry: `Reverted to <d MMM HH:mm> — N changes discarded`. The time is entry k's (with the year when it isn't the current year), N is the number of entries after k, and it says `1 change` for one.
  - That entry's ledger records every field the revert changed, from before the revert to after, and the comments it removed or brought back. A later revert can walk back through it.
  - `updated` = now.
  - A changed title renames the file. A changed column puts the task at the top of that column.
- **Stale view:** the request carries k and a fingerprint of what the person saw: the history's length and entry k's `at` and `text`. If the file no longer matches, main refuses with "This task changed since you opened its history. Check it and try again." and writes nothing.

### Staleness

- **Working days:** `staleDays` counts the Monday to Friday dates after the local date of `updated`, up to and including today's local date. It is never negative, and it ignores daylight saving and public holidays.
  - Updated today: 0. Updated on Friday or Saturday, today Monday: 1.
- **Age tiers** (thresholds are named constants in `src/domain/staleness.ts`):

  | Working days | Level | Tier |
  | --- | --- | --- |
  | 0–1 | `green` | On track |
  | 2–3 | `amber` | Needs a nudge |
  | 4–5 | `orange` | Stalling |
  | 6 or more | `red` | Stale |
  | any, in Done | `grey` | Complete |
  | any, archived | `grey` | Archived |

- Every task shows its count as `Nd`, Done and archived tasks included.

### Project

Source: [Project and responsibility fields](https://github.com/marcusrohden/mboard/issues/7).

- **Project:** optional.
  - **Normalising:** trim it and collapse repeated spaces. Empty becomes `null`.
  - **Canonical spelling:** if it matches an existing project ignoring case, use the existing spelling.
  - **Suggestions:** distinct projects from all tasks (board and archive), most recent `updated` first, filtered by a case-insensitive substring.
- **Responsibility:** removed. Who has the next step is now the column (Internal or With client). ADR 0006 supersedes this part of the ticket; section 3 covers files that still carry the key.

### Due dates and reminders

Source: [Due dates and reminders](https://github.com/marcusrohden/mboard/issues/11).

- **Due date:** optional, `YYYY-MM-DD`.
- **Due status** (relative to today's local date):
  - `overdue` if before today
  - `today` if equal
  - `upcoming` otherwise
  - `none` if there's no due date
  - The board styles `today` amber and `overdue` red, except in Done, where the chip is always neutral.
- **Reminder eligibility:** a task is eligible when all of these hold:
  - it isn't archived and isn't in Done
  - it has a due date
  - either `due < today`, or `due == today` and the local time is 09:00 or later
  - its key `${created}|${due}` isn't in the fired set
- **Delivery:**
  - One eligible task: one notification, "Due today: <title>" or "Overdue: <title>". Clicking it opens that task.
  - Two or more at once: one grouped notification, "N tasks due", with the titles in the body. Clicking it opens the board.
  - Keys are added to the fired set when delivered or when delivery fails. They're pruned when their task no longer exists.
- **When it checks:** at launch, every 60 seconds, and when the Mac wakes.
- **If notifications fail:** if the notifier reports failure, the reminders go to the **reminder banner**, an in-app list shown at the top of the board until it's dismissed, and the tray menu shows "Notifications unavailable".
- **Menu-bar count:** tasks not archived, not in Done, with `due <= today`. Hidden when it's 0.

### Search and filters

Source: [Search and filtering](https://github.com/marcusrohden/mboard/issues/8).

- **Search:** split the query on whitespace. Each term must appear, ignoring case, in at least one of: title, description, any comment text, project.
- **Filters** are combined with AND:
  - **Projects:** a set of project names, where `null` means No project. Empty set means any.
  - **Due:** `any`, `overdue`, `today`, `thisWeek` or `none`. `thisWeek` means today up to and including the coming Sunday, with Monday-start weeks.
  - **Stale only:** staleness level is `amber`, `orange` or `red`, that is 2 working days or more and never Done or archived.
- **Archived view:** search and Projects only.
- **Persistence:** nothing persists between launches.

### Outside edits

Source: [Edits made directly in Obsidian](https://github.com/marcusrohden/mboard/issues/9).

- **Watching:**
  - Recursive watch of the board folder, ignoring dot-files and anything outside `tasks/` and `archive/`, debounced by 250 ms.
  - A full rescan when the window gains focus.
  - After every scan, push a fresh snapshot to the renderer.
- **Never written in reaction:** an outside edit never triggers a write, an `updated` bump or a history entry.
- **Read-modify-write:** every app change re-reads the file from disk, parses it, applies one change and writes it back. It never serialises a stale in-memory copy.
- **Unreadable files:** a file whose frontmatter isn't valid YAML, or isn't a mapping, is listed as unreadable with a reason, and never written.
- **Files with no frontmatter** are tasks. The whole body is the description, and defaults apply.

## 3. Board folder and task file format

Sources: [Task file format](https://github.com/marcusrohden/mboard/issues/12) and [First run](https://github.com/marcusrohden/mboard/issues/10).

**Layout**

```text
<board folder>/
├── README.md     written once at setup: what the board is and the file format, for people and agents
├── tasks/        live tasks (any column)
└── archive/      archived tasks
```

**Task file**

```markdown
---
title: "Why is the staging build failing?"
status: With client
project: Acme website
due: 2026-11-20
created: 2026-11-16T09:30:00
updated: 2026-11-16T14:03:12
order: 2
---

## Description

The staging pipeline fails at the asset step since Friday.

## Comments

### 2026-11-16 14:02

Asked the client for the staging credentials.

## History

- 2026-11-16 09:30 — Created in To do <!-- mboard-ledger {"v":1,"at":"2026-11-16T09:30:00","changes":[…]} -->
- 2026-11-16 10:05 — Moved from To do to In progress <!-- mboard-ledger {"v":1,"at":"2026-11-16T10:05:41","changes":[{"field":"status","from":"To do","to":"In progress"}]} -->
- 2026-11-16 14:02 — Comment added <!-- mboard-ledger {"v":1,"at":"2026-11-16T14:02:09","changes":[{"field":"comments","added":[{"at":"2026-11-16 14:02","text":"Asked the client for the staging credentials."}],"removed":[]}]} -->
- 2026-11-16 14:03 — Moved from In progress to With client <!-- mboard-ledger {"v":1,"at":"2026-11-16T14:03:12","changes":[{"field":"status","from":"In progress","to":"With client"}]} -->
```

**Frontmatter when writing**

- Known keys go in this order: `title, status, project, due, created, updated, archived, order`.
- `status` is the exact column name, or the file's own spelling while it's kept (see Reading).
- `responsibility` is never written (see Reading).
- Keys with no value are omitted: `project`, `due`, `archived`, `order`.
- Unknown keys are kept and written after the known ones, in their original order.
- Use the YAML core schema, so dates stay strings. Quote strings only when YAML needs it; `title` is always double-quoted.

**Body when writing**

- Sections in this order: `## Description`, `## Comments`, `## History`, each followed by a blank line.
- An empty Comments or History section is still written, with its heading.
- Each comment is `### YYYY-MM-DD HH:mm`, a blank line, then the text.
- Each history entry is `- YYYY-MM-DD HH:mm — <text>`, with an em dash, then a space and its **ledger comment**, `<!-- mboard-ledger <json> -->`, on the same line (ADR 0005).
  - The JSON is `{"v":1,"at":"YYYY-MM-DDTHH:mm:ss","changes":[…]}`, with keys in that order and seconds in `at`. Each change is either `{"field","from","to"}` for one value (`null` when empty) or `{"field":"comments","added":[…],"removed":[…]}` with `{"at","text"}` comments.
  - Value fields: `title`, `status`, `project`, `due`, `description` (the full text) and `archived`.
  - The JSON is written by `JSON.stringify`, which escapes line breaks and control characters. On top of that, `<`, `>`, U+2028, U+2029 and a `-` that starts a `--` run are written as `\uXXXX`, so the comment is always one line, can't be closed early and stays readable.

**Reading** is tolerant:

- **Frontmatter:** only a block that starts on line 1 counts. Keys are case-sensitive. `key:`, `key: null` and a missing key all mean empty.
- **Status:**
  - Matched ignoring case and surrounding spaces.
  - An unknown status reads as `To do`. The raw value isn't rewritten until the status changes.
- **Legacy `responsibility`** (files from before ADR 0006, written by the app, Obsidian or an agent):
  - If the status matches `To do` or `In progress` (any spelling that matches) and `responsibility` matches `Client` or `Internal` ignoring case and surrounding spaces, the task reads as `With client` or `Internal`.
  - Otherwise the status is unchanged: for `Done`, the two new columns, an unknown or missing status, and any other responsibility (`Me`, unknown, empty).
  - The key is read but never kept, so the next app write drops it and writes the effective `status`.
  - That fix-up isn't an update: no `updated` bump and no history entry. It rides along with whatever write comes next, including a reorder.
  - Archived files follow the same rule.
- **Timestamps:**
  - `created`, `updated` and `archived` also accept a space instead of `T`, a missing seconds part, or an offset (converted to local time).
  - When a timestamp is unparseable or missing, fall back to the file's birth time for `created` and its modification time for `updated`.
- **Body sections:**
  - The body is split only at `## Comments` and `## History` headings (matched ignoring case).
  - The Description section runs from `## Description` (or the start of the body, if that heading is missing) up to the first of those.
  - Any other heading belongs to the description.
- **Comments:** each starts at a `### <date time>` heading; a heading that doesn't parse as a date and time is kept as comment text. Any text in the Comments section before the first heading is kept as an undated comment.
- **History:** lines starting `- `. A line without the expected date prefix is kept with an empty `at`.
  - **Ledger comment:** only a `<!-- mboard-ledger … -->` comment at the very end of the line counts. A line without one, or with one that isn't a valid version 1 ledger, is a **legacy entry**: its whole text is kept as it is and it has no ledger data.
  - A change to a field this version doesn't track (for example one an older or newer mboard tracked) is kept and written back, but never reverted.
- **Title:** the `title` property, else the file name without `.md`.
- **Round-trip:** parsing a file written by the app and serialising it gives identical bytes.

**File names**

- Built from the title:
  - NFC-normalise
  - drop control characters and `/ \ : * ? " < > | # ^ [ ]`
  - collapse whitespace and trim
  - strip leading dots and trailing dots and spaces
  - cut to 100 characters
  - fall back to `Untitled` if nothing is left
  - add `.md`
- A clash with another file in the target folder (case-insensitive) adds ` 2`, ` 3` and so on.
- The app renames the file when the title changes, or when an archive or restore move needs a free name.

**Task id:** the file's path relative to the board folder, with `/` separators, for example `tasks/Fix login bug.md`.

- Main accepts only ids matching `^(tasks|archive)/[^/\\]+\.md$` whose resolved path stays inside the board folder.
- Any other id is rejected with an error.

**Safe writes**

- Write `<dir>/.<name>.mboard-tmp`, then rename it over the target.
- Writes to one path are serialised.
- Archive, restore and rename use `fs.rename`.
- `tasks/` and `archive/` are created on demand if missing.

**Board README:** written once at setup. It describes the folder, the five status values (what Internal and With client mean), the properties table and the body sections, so an agent can read and write tasks correctly. It is never rewritten, so a README from before ADR 0006 still mentions `responsibility`.

## 4. First run, settings and folder problems

Source: [First run](https://github.com/marcusrohden/mboard/issues/10).

**Settings**

- `settings.json` in `app.getPath('userData')`:

  ```ts
  { boardPath: string | null; openAtLogin: boolean; windowBounds?: { x: number; y: number; width: number; height: number } }
  ```

- Written atomically.
- Missing or invalid settings mean `boardPath: null` and `openAtLogin: true`.

**Classifying a chosen folder**

| Situation | Result |
| --- | --- |
| Hidden folder (its name starts with `.`), or inside `.obsidian/` or `.trash/` | rejected |
| Has a `tasks/` subfolder | open as an existing board |
| Has no non-hidden entries, and has no `*.icloud` placeholder | new board: create `tasks/`, `archive/` and `README.md` |
| Anything else | rejected, "This folder isn't empty and isn't an mboard board." |

- **Vault check:** for new and existing boards, if no folder from the chosen one up to `/` holds `.obsidian/`, ask for confirmation: "This folder doesn't look like it's inside an Obsidian vault. Use it anyway?"
- **Saving:** on acceptance, save `boardPath`. If this is the first setup and `openAtLogin` is true, apply the login item.

**At launch**

- **No `boardPath`:** the setup screen.
- **The path doesn't exist:** the "Can't open your board" screen, reason `notFound`.
- **Reading it throws EACCES or EPERM:** the same screen, reason `permissionDenied`.
- **It isn't a directory:** the same screen, reason `notADirectory`.
- The screen offers **Try again** and **Choose folder…**.
- The board folder itself is never created except through setup.

**Change board folder…** (app menu and tray menu): the same picker and classification. Files are never moved. When it's started from a menu, main shows a rejection or the vault warning as a native message box (the warning with **Use anyway** and **Cancel**), then pushes the new app state to the renderer.

**Change folder…** in Settings: the same picker and classification, with a rejection or the vault warning shown inline in the dialog, as on the setup screen.

## 5. Screens

Source: [Board and task screens](https://github.com/marcusrohden/mboard/issues/13).

- **Header:**
  - board name (the folder name)
  - search box (`/` focuses it)
  - filter controls: Project (multi), Due (single), Stale only (toggle)
  - **Clear**, shown when anything is active
  - **New task** (`N`)
  - **Archived**, a toggle
  - **Settings**, a gear button at the far right, with the tooltip "Settings (⌘,)"
  - **Change board folder…** reachable from the app menu
- **Notices:**
  - an "N files couldn't be read" notice (expandable: path and reason)
  - the reminder banner
  - the new version notice, at the top of the window on every screen (see Settings and app updates below)
- **Board:**
  - Five columns, each with its name and a count, shown as "shown of total" while filtered.
  - Done also has **Archive all**.
  - **Width:** the columns share the width equally, down to a minimum of 160 px each. Below that (always at the 720 px minimum window, and with the drawer open) the board scrolls horizontally. A column header wraps rather than overflowing.
  - Empty board: "No tasks yet" with a **New task** button.
- **Task on the board:**
  - title, clamped to 2 lines
  - project label
  - due chip (date as `d MMM`, for example `20 Nov`): neutral, amber "Today", red "Overdue"
  - a small muted line, `Created 12 Nov · Updated 14 Nov` (`d MMM`, with the year when it isn't the current year), then the **age chip** `Nd` coloured by its tier
  - the age chip's tooltip and accessible text give both times, the count and the tier, for example `Created 12 Nov 08:00 · Updated 14 Nov 09:12 — 3 working days, Needs a nudge`
  - the 4 px left edge has the tier's colour too
  - Done tasks show an **Archive** button on hover and focus.
  - The whole task is a drag handle and opens the detail on click or Enter.
- **Drag and drop:** `@dnd-kit/react` sortable lists across the columns, with mouse and keyboard.
  - All dnd-kit imports stay in one board adapter module.
  - The write happens on drop only.
  - The renderer sends `moveTask(id, status, beforeId)`, where `beforeId` is the task the dropped one now sits above, or `null` for the end of the column.
- **New task dialog:**
  - Fields: Title (required), Column (all five, default To do), Project (input with a suggestion list), Due date (`<input type="date">`), Description (textarea).
  - Enter in the title, or Cmd+Enter anywhere, creates the task. Esc cancels.
- **Task detail drawer** (right side, the board still visible):
  - Fields:
    - Inline-editable title, column select (all five columns), project (with suggestions), due date (with clear) and description.
    - Each saves on blur or Enter (Cmd+Enter for the description).
    - Created and updated times are shown, with the age chip beside Updated.
  - **Save** (top right) commits the field still being edited, waits for that save, then closes the drawer. If the save fails, the drawer stays open and the error shows as a toast.
  - Comments:
    - Oldest first, each with its timestamp.
    - A textarea plus **Add comment**; Cmd+Enter posts.
  - History: collapsible, newest first.
    - Every entry the task can be reverted to has a quiet **Revert to here** button. It opens a confirmation dialog: title "Revert task?", message "“<title>” will go back to how it was at 16 Nov 14:02. The N changes made after that will be removed from the task and its history.", **Cancel** (initial focus) and **Revert** (danger). Cancel changes nothing.
    - The latest entry has no control. Other entries that can't be reverted to say briefly why; the reason for entries from before the ledger shows once, on the newest of them. An archived task says to restore it first.
  - Actions:
    - **Mark complete** when not in Done
    - **Archive** when in Done
    - **Restore** when archived
    - **Delete** (confirm)
    - **Open in Obsidian**
  - **Archived tasks:** all fields read-only.
  - **Outside changes:** fields refresh from new snapshots, except the field being edited.
  - If the task disappears, the drawer closes with a brief notice.
- **Archived view:** replaces the board with a list sorted by `archived` descending (missing values last).
  - Columns: title, project, archived date.
  - Search and the Projects filter apply.
  - A row opens the detail drawer.
- **Setup screen:** a short explanation, **Choose folder…**, inline errors, and a confirm step for the vault warning.
- **Can't open your board screen:** the path, the reason in plain words, **Try again** and **Choose folder…**.
- **Settings dialog:** a modal labelled "Settings", hosted for the whole app so it opens on the setup, "Can't open your board" and board screens. It opens from the header's gear, and from **Settings…** in the app menu (⌘,) and the tray menu. While it's open, the board's single-key shortcuts are off. **Done** or Esc closes it. Sections:
  - **Board folder:** the current path (or "Not chosen"), and **Change folder…**.
  - **Open at login:** a checkbox that calls `setOpenAtLogin`.
  - **Notifications:** whether they work, from `notificationsAvailable` (not known yet, working, or unavailable with a pointer to System Settings › Notifications).
  - **App updates:** "mboard X.Y.Z", a status line, **Check for updates** (disabled while checking, downloading or installing), and for a new version either **Install and restart** with **Release notes**, or **Download from GitHub** with the reason this copy can't install it itself.
- **New version notice:** "mboard X.Y.Z is available." with **Install and restart** (or **Download from GitHub** when this copy can't install it), **Release notes** and **Later**. Later hides it for that version until the next launch; a newer version shows it again. It also shows the download and install while they run, and an install that failed with **Download from GitHub**.
- **Look:**
  - plain CSS (CSS modules or one stylesheet with custom-property tokens), no UI kit
  - follows the system light and dark mode
  - compact, macOS-like, system font
  - visible focus rings
  - Australian English in all UI text

## 6. Platform behaviour

Source: [Due dates and reminders](https://github.com/marcusrohden/mboard/issues/11).

- **Window and app lifecycle:**
  - A single-instance lock: a second launch focuses the existing window.
  - The app menu: About mboard, **Settings…** (⌘,), **Change board folder…**, then Services, Hide, Hide Others, Show All and Quit. Settings is a menu accelerator because the renderer's shortcuts ignore keys pressed with a modifier.
  - Closing the window hides it and hides the Dock icon. The app keeps running.
  - Cmd+Q (the app menu's Quit, or the tray's Quit) quits.
  - Window bounds are saved and restored.
- **Tray:**
  - A template icon. Its title is the due/overdue count, or empty when that's 0.
  - Menu items:
    - **Open mboard**
    - **Settings…**
    - **Change board folder…**
    - **Open at login** (checkbox)
    - "Notifications unavailable" (disabled, only after a failure)
    - **Quit**
- **Open at login:** `app.setLoginItemSettings({ openAtLogin })`, kept in sync with settings.
- **Notifications:** Electron `Notification`.
  - The notifier resolves `shown` on the `show` event, and `failed` on the `failed` event or when `Notification.isSupported()` is false.
  - The result is logged to `userData/mboard.log`.
  - Clicking a notification shows the window and opens the task (or the board, for a grouped one).
- **Open in Obsidian:** `shell.openExternal('obsidian://open?path=' + encodeURIComponent(absolutePath))`.
- **Settings…** (app menu and tray): shows the window, sets a pending request and pushes `openSettings`. The renderer takes the request with `takeOpenSettingsRequest()` both when the push arrives and when it mounts, so a window that is still loading opens Settings too, and a reload doesn't open it again.
- **App updates** ([ADR 0004](../adr/0004-in-app-updates-from-github-releases.md)):
  - **Source:** `GET https://api.github.com/repos/marcusrohden/mboard/releases/latest`, without a token, through `net.fetch` in main. A 404 means nothing has been released. The release's version is its tag (`vX.Y.Z`). It counts only once its asset `mboard-darwin-<arch>-X.Y.Z.zip` has the state `uploaded`. An asset without a `sha256:` digest can only be downloaded from the release page.
  - **Checks:** in a packaged build, 10 seconds after launch and every 6 hours, quietly: they never show `checking`, and a failed one leaves the last result in place. **Check for updates** shows `checking` and any failure.
  - **Status:** `idle`, `checking`, `upToDate` (with the time checked), `available` (the version, and why this copy can't install it, if it can't), `downloading`, `installing`, or `failed` (a plain-words message, and the version for a failed install).
  - **Can't install itself** when it runs from source, isn't inside a `.app` bundle, runs from an `AppTranslocation` path, or can't write to the bundle's folder.
  - **Install:** download into `<temp>/mboard-app-update-<version>-<random>/` and check the size and SHA-256, unpack with `ditto -x -k`, delete the zip, check that the bundle id equals the running app's and `CFBundleShortVersionString` equals the version, and strip the quarantine flag (best effort). Then a detached `/bin/sh` helper waits up to 60 seconds for mboard's process to exit, moves the running bundle to a hidden backup beside it, moves the new bundle into place (restoring the backup if that fails), removes the backup and the staging folder, and opens the bundle. mboard quits as soon as the helper has started.
  - **Cleanup:** the staging folder is removed on success and on every failure, including a download stopped by quitting. Leftover staging folders and the backup are removed at launch.
  - **Release page:** `openAppUpdateReleasePage()` opens the known new version's release page, or the latest release, and only URLs under `https://github.com/marcusrohden/mboard/releases/`.

## 7. Architecture

```text
src/domain/    pure TypeScript: model, file codec, rules. No node, electron or DOM imports.
src/shared/    the bridge contract: MboardApi, DTOs, IPC channel names.
src/main/      Electron main: composition root, services, ipc, platform.
src/preload/   contextBridge exposing window.mboard; no logic.
src/renderer/  React UI; talks only to window.mboard.
tests/e2e/     Playwright Electron tests.
```

**Rules**

- The renderer never computes "now". It uses the `now` and `today` carried in every `BoardSnapshot`.
- The main process owns the clock and pushes a new snapshot at least once a minute (from the reminder tick), so the UI rolls over at midnight.
- All file access is in main. Only ids cross the bridge, never paths, apart from the board path shown in the UI.

### Bridge contract (`src/shared/contract.ts`)

**Errors:** a rejected command (an unknown id, a missing file, an edit to an archived task, invalid input) throws an `Error` whose message is user-presentable. The renderer shows it in a toast.

### Test hooks (environment variables read by main)

| Variable | Effect |
| --- | --- |
| `MBOARD_USER_DATA` | overrides the user-data folder (settings, reminder state, log) |
| `MBOARD_BOARD_PATH` | the board path to use at launch, instead of settings. If the folder is a new-board candidate, set it up without dialogs |
| `MBOARD_FAKE_NOW` | a fixed local `YYYY-MM-DDTHH:mm:ss` for the clock |
| `MBOARD_NOTIFIER_LOG` | use a fake notifier that appends JSON lines (`{title, body, taskId}`) to this file |
| `MBOARD_NOTIFIER_FAIL=1` | the fake notifier returns `failed` |
| `MBOARD_TRASH_DIR` | delete moves files into this folder instead of the macOS Trash |
| `MBOARD_DISABLE_LOGIN_ITEM=1` | never call `setLoginItemSettings` |
| `MBOARD_DISABLE_APP_UPDATE_CHECK=1` | never check for a new version by itself (Settings can still check) |

E2E tests must always set `MBOARD_USER_DATA`, `MBOARD_TRASH_DIR`, `MBOARD_DISABLE_LOGIN_ITEM` and `MBOARD_DISABLE_APP_UPDATE_CHECK`, so they never touch the real vault, real settings or the login items, and never reach GitHub. Today the fixtures set only `MBOARD_USER_DATA` and `MBOARD_DISABLE_APP_UPDATE_CHECK`.

## 8. MVP acceptance checklist

Each item names where it's verified: **U** unit, **I** integration (real temp folders), **E** Playwright end-to-end. The MVP is done when every automated item passes.

1. **First run.** With no settings, the setup screen shows. Choosing an empty folder inside a fake vault creates `tasks/`, `archive/` and `README.md`, then shows the empty board. **E** (dialog stubbed in main) **U** (classification)
2. **Folder checks.**
   - A folder that isn't empty and isn't a board is rejected.
   - A folder outside a vault asks for confirmation.
   - An existing board opens.
   - A hidden folder is rejected.

   **U** **E** (one path)
3. **The board folder persists across a relaunch.** **E**
4. **A missing board folder at launch** shows "Can't open your board". **Choose folder…** recovers. **E**
5. **Create a task with every field.**
   - The file has the expected frontmatter and body, and `created == updated`.
   - The history log says `Created in To do`.
   - The task shows at the top of To do.

   **U** **E**
6. **Editing each field** updates the file, bumps `updated` and adds exactly one history entry. An unchanged value adds nothing. A title change renames the file. **U** **I** **E** (title and project)
7. **Adding a comment** appends it under Comments with its timestamp, and the history log says `Comment added`. **U** **E**
8. **Moving.**
   - Moving by drag and by **Mark complete** updates `status` and adds a history entry.

   - Reordering within a column changes only `order`.

   **U** **I** **E**

16. **Reminders.**
   - With the fake clock at 09:00 and a task due today, the fake notifier gets one reminder, and it isn't repeated.

   - Done and archived tasks never remind.

   **U** **E**

18. **Closing the window** leaves the app running with the window hidden, and the tray exists. **E**

   - Ids escaping the board folder are rejected.
